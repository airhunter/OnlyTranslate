专题 2

我们现有类 Readability 方案，在新流程里起什么作用？

简短答案：它很有用，但它应该负责“找到主内容根”，不应该负责“每一个节点最终翻不翻”。把职责放对，才能减少跷跷板。

Readability 类方案最擅长什么？

左侧噪声 导航/广告/推荐
中间正文根 Readability 擅长找到这里
右侧混合区 可能有相关内容，也可能是 metadata
定位：

Readability 像“雷达”，帮我们定位主要阅读区域。它不是“法官”，不应该单独决定每个卡片、标签、人名、日期是否翻译。

点一个页面情况，看 Readability 应该怎么参与

为什么不能让 Readability 负责所有判断？

它偏向长正文

短标题、卡片简介、折叠详情、论坛帖子可能分数不够，却确实该翻。

它不懂站点业务

CNN 的 lead package、TDS 的 Related Articles、GitHub README 都有特殊结构。

它难以区分 metadata

作者、日期、分类、标题都可能是短文本。只靠正文密度很难稳定区分。

新流程里，它的位置应该是这里

1
Readability / 主内容检测

找到 primary content root，给主内容高优先级。

2
DOM 单位化

把 root 内外的候选节点整理成 paragraph/card/title/summary。

3
语义分类

判断 content、metadata、action、related-title、related-summary。

4
策略决策

hard skip、soft skip、allow override，最终决定翻不翻。

Readability 的输出应该类似： { primaryRoot: articleElement, confidence: 0.84, reason: "dense paragraphs inside article" } 然后交给后面的层继续判断节点，而不是直接翻整个 root。
