专题 A：Read Frog DOM Walker

Read Frog 是怎么把 DOM 变成可翻译单位的？

它不是先问“这是不是正文”。它先做一件更机械、更可靠的事：递归遍历 DOM，把每个元素标成 paragraph、block、inline 或 skip。翻译阶段再根据这些标记决定整体翻、拆开翻，还是跳过。

它靠大量规则吗？不是。规则少，但位置关键

Read Frog 的规则大体只有三类。真正复杂的是网页 DOM 本身，不是它的规则表。

规则组 代表内容 它解决什么 它不解决什么
不可遍历标签 HEAD、SCRIPT、STYLE、IMG、VIDEO、INPUT、SVG 避免翻译无意义或危险区域。 不知道某个普通 div 是广告还是正文。
强制 block 标签 BODY、H1-H6、UL、LI、ARTICLE、SECTION、FIGURE、NAV 让大结构稳定，不被 display 或内联文本误导。 不知道 SECTION 里是正文、推荐区还是评论区。
CSS display 判断 inline、inline-block、contents、ruby 算 inline-like。 适应现代网页里用 CSS 改变语义标签表现的情况。 不知道按钮文案是否值得翻译。
少量站点选择器 GitHub、YouTube、Reddit 等少量 custom selector。 跳过已知站点里非常明确的噪声区域。 不是完整站点语义分类系统。
关键区别：

Read Frog 的“分类”是 DOM 形状分类，不是内容角色分类。所以它能回答“这个节点像一段吗”，但不能稳定回答“这个 Related card 里的日期要不要翻”。

为什么先标 paragraph / block / inline 对翻译有帮助？

因为翻译时最怕父子重复、行内文本被拆碎、块级布局被塞乱。标记之后，翻译阶段就有了稳定的拆分单位。

情况 1：paragraph 里没有 block 子节点

例子：<p>This is a paragraph with <a>a link</a>.</p>

做法：把整个 p 当成一个翻译单位。这样链接和上下文一起翻译，语义更完整。

情况 2：paragraph 里有 block 子节点

例子：<div>text <section>block</section> text</div>

做法：连续 inline 文本合并成片段，block 子节点递归翻译。避免把整个大容器一次性翻掉。

情况 3：节点被标成 skip

例子：<nav>Home Products Pricing</nav>

做法：不走进去，也不把它当候选。减少导航、按钮、隐藏文本的误翻。

Read Frog 翻译阶段的简化逻辑： if element has paragraph label: if no block child: translate(element) else: translate(consecutive inline nodes) recursively translate(block child) else: walk children
