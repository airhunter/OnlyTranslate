专题 3

这个方案会不会过度复杂，最后更难排错？

你的担心是合理的。所以这里不讲“理想大架构”，只讲怎么把风险压低：先做最小版本，必须可观测，必须有回归样本，必须能回退。

先把风险说清楚

风险 1：规则变多

如果每个站点都加一堆 if，最后没人知道为什么翻或不翻。

风险 2：效果不稳定

看起来分类很精细，但真实网页 DOM 千变万化，可能仍然误判。

风险 3：排错困难

用户说“不对”，如果没有决策日志，我们只能继续猜。

所以不要一次性上完整方案，要做“复杂度预算”

最小可落地版本

新增概念
低
通用规则改动
低
站点特例数量
中
可观测性
高

先不做什么

  • 不引入 LLM 做页面节点分类。
  • 不重写整个翻译引擎。
  • 不把 Read Frog 的 walker 全套搬过来。
  • 不一次性支持所有站点。
第一阶段只做： 1. 调整 skip / profile 的优先级模型 2. 给 TDS Related Articles 做结构化 allow 3. 输出可调试 decision reason 4. 加回归测试样本

点一个排错场景，看新方案怎么定位问题

推荐分阶段落地，不做“大爆炸重构”

阶段做什么成功标准失败时怎么办
阶段 1 TDS 专项：Related 标题/简介翻译，metadata/social 跳过 修复当前三张截图，不破坏现有正文翻译 回退 TDS profile，不影响通用逻辑
阶段 2 把 hard/soft skip 模型抽成小函数 GitHub、CNN、How LLMs Work 测试继续过 只保留站点 profile，暂不启用通用分类
阶段 3 增加 debug decision 输出 看到每个节点为什么翻/不翻 只在 dev/debug 开关下启用
阶段 4 逐步吸收 Read Frog 的单位化思路 减少父子重复翻译和排版错位 局部启用，先不替换旧 walker

最终判断：方案可以做，但必须保持克制

我不建议现在就做一个完整“大而全”的分类系统。

我建议先做 TDS 这个问题所需的最小分层：hard/soft skip + related card title/summary allow + decision reason。这样既能解决当前问题，又不会把系统变成难以排错的黑盒。
