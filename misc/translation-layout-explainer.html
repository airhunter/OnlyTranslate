已有专题

Read Frog 值得借鉴的不是“语义分类”，而是“DOM 单位化”

它没有判断“这是作者”“这是相关推荐 metadata”。它做的是更底层、更稳定的一件事：把复杂 DOM 标成 paragraph、block、inline，然后再翻译。

Read Frog 做得好的部分

可借鉴 一次递归打标签，而不是每次翻译临时猜。

可借鉴 用 CSS display 和少量 tag 常量区分 block / inline。

可借鉴 对隐藏节点、不可走节点、顶层 nav/header/footer 先剪枝。

可借鉴 翻译时按连续 inline 片段合并，降低父子重复翻译。

它没有直接解决的部分

仍需我们做 Medium/TDS 的作者、日期、标签、社交按钮是否该翻。

仍需我们做 CNN 首页这类非文章页的主标题、卡片标题。

仍需我们做 Asterisk 脚注译文插入后如何触发站点重排。

仍需我们做 How LLMs Work 折叠卡片展开后如何重新翻译。

一句话：

Read Frog 的 walker 能帮我们把“节点形状”稳定下来，但“节点角色”仍然需要 OnlyTranslate 自己做策略。

推荐改造方向：先分职责，不急着大重构

这不是要把系统改成一个庞大黑盒。相反，是把现在混在一起的判断拆开，便于定位问题。

第一步

引入可解释的候选单位

借鉴 Read Frog：先知道一个节点是 paragraph、block、inline、card title 还是连续 inline 片段。

第二步

保留站点 profile

TDS、CNN、GitHub 这种差异很大的站点，继续用 site profile 提供局部规则。

第三步

输出决策理由

每个节点翻或不翻，都能看到：命中哪个 skip、哪个 profile、哪个分类。

推荐的最小落地边界： 1. 先不替换整个翻译引擎 2. 先把候选节点的来源和拒绝原因记录清楚 3. 站点特例只修当前明确的问题 4. 每次修一个站点，都补一个回归样本

用真实问题看：每一层应该负责什么

点左侧案例，右侧会显示这类问题应该在哪一层修。这样以后不会看到一个问题就去改全局规则。

最后，把“靠大量规则吗”说清楚

Read Frog 的底层 walker 不是靠几百条业务规则。它靠的是三类少量规则，再加递归。

规则类型 例子 作用 风险
不遍历规则 script、style、input、img、hidden、aria-hidden、顶层 nav/header/footer 先剪掉明显不该翻或不能翻的区域。 如果站点把正文放在奇怪容器里，可能误伤。
强制 block 标签 h1-h6、p 的父层、li、section、article、figure、main 避免把大容器当成一整段，也避免 inline 合并过头。 它只看形状，不懂业务意义。
CSS display 判断 inline、inline-block、contents、ruby 算 inline；其他多半算 block。 适应现代网页里 div/span 被 CSS 改变显示类型的情况。 动态样式、虚拟列表、隐藏展开仍需额外处理。
