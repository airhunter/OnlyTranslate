OnlyTranslate 实施方案

页面翻译识别与排版问题的改造计划

这页讲的不是文档怎么组织，而是 OnlyTranslate 项目接下来应该怎么改代码：哪些模块负责候选收集、skip、site profile、Readability、动态扫描和译文插入，怎么避免继续变成“修 A 坏 B”的跷跷板。

先定目标：不是“更激进翻译”，而是“可解释地翻对地方”

这次改造要把翻译目标识别从一团混合逻辑，拆成可观察、可测试、可局部回退的流程。

目标 1

减少多翻

TDS 的社交链接、作者、日期、分类、阅读时长、分享按钮不应被翻译。

目标 2

减少漏翻

TDS 相关文章标题/简介、CNN 首页 lead 标题、展开后的内容应该被翻译。

目标 3

减少排版错位

脚注、折叠卡片、GitHub README、卡片列表的译文必须放在正确容器里。

约束：

不建议一次性重写整个翻译引擎。先把容易出错的决策点拆清楚，再逐步替换最有收益的部分。

目标流程：每一层只做一件事

当前的问题很大一部分来自职责混在一起：候选收集时顺便判断语义，site profile 顺便覆盖 skip，插入层又承担布局修复。改造后每层只输出自己的结论。

代码结构组织：核心逻辑分层，站点规则收口

我的组织原则是：通用能力放在 engine/utils，站点差异放在 siteProfiles，翻译流程只编排，不塞具体站点判断。

建议目录结构

entrypoints/main/ trans.ts 只负责翻译流程编排：收集目标 -> 翻译 -> 插入 dom.ts 保留 DOM 遍历入口，但逐步减少站点语义判断 translationTarget/ collect.ts 收集候选节点 decision.ts 统一输出 allow / skip / reason dynamic.ts 处理展开、懒加载、DOM mutation unitizer.ts 借鉴 Read Frog 的 paragraph / block / inline 单位化 siteProfiles/ types.ts 定义 profile 能力边界 medium.ts TDS/Medium 结构规则 cnn.ts CNN 首页/新闻卡片结构规则 github.ts GitHub README 结构规则 asterisk.ts 脚注布局 hook

依赖方向

trans.ts -> translationTarget/collect.ts -> translationTarget/decision.ts -> siteProfiles/index.ts -> contentFilter / contentDetector -> layout hook 禁止反向依赖： siteProfiles 不直接调用 trans.ts contentFilter 不知道具体站点复杂 DOM contentDetector 不决定每个节点是否最终翻译 layout hook 不参与候选识别
关键约束：

站点 profile 可以提供“这个结构里哪些节点应该 allow/skip”，但不要变成绕过所有全局安全过滤的后门。

translationTarget

实施阶段：小步改，不做大爆炸

每一步都有成功标准和回退边界。这样如果某一步效果不好，可以只回退局部。

0

补齐基线样本

先把现在反复出问题的页面变成测试样本：TDS、CNN、How LLMs Work、GitHub README、Asterisk 脚注。

  • 记录哪些节点应该翻。
  • 记录哪些节点不应该翻。
  • 记录译文应该 append 到哪里。
成功标准

先有红灯测试，不靠截图记忆。

1

引入 decision reason

不先改大量规则，而是让系统能说清楚“为什么翻/不翻”。

  • 候选来源：main root / profile / dynamic / manual。
  • 过滤原因：hard skip / soft skip / profile allow。
  • 插入目标：原节点后、父容器内、站点 hook。
成功标准

排错不再靠猜。

2

修 TDS：Related allow + metadata skip

这是当前最典型的跷跷板问题：相关文章标题/简介要翻，但作者、日期、分类、社交不翻。

  • Medium/TDS profile 结构化识别 related card。
  • 只 allow card title 和 summary。
  • hard skip social/share/author/date/read-time/tags/CTA。
成功标准

三张 TDS 截图中的多翻消失，Related 标题/简介保留翻译。

3

修 CNN：首页 lead package

CNN 首页不是文章页，Readability 不稳定。这里应该走 CNN profile。

  • 识别 container lead package title/headline。
  • 跳过 nav、watch/listen、ad、sign in。
  • 避免把子卡片图片 alt、广告字幕等当正文。
成功标准

红框主标题翻译，导航和广告不翻。

4

修动态内容和插入位置

How LLMs Work 折叠卡片展开后要触发翻译，译文不能跑到折叠容器外。

  • 动态扫描监听 aria-expanded / hidden / class / style。
  • 扫描新出现的可见内容，而不是隐藏时提前翻译。
  • appendTarget 必须指向展开内容容器内部。
成功标准

折叠时不露译文，展开后自动翻译。

5

局部吸收 Read Frog 的 DOM 单位化

不是照搬 Read Frog，而是借鉴它的 paragraph/block/inline 标记，让候选单位更稳定。

  • 先用于 debug 和测试解释。
  • 再用于减少父子重复翻译。
  • 最后才考虑替换部分 grabNode 逻辑。
成功标准

减少重复翻译，不扩大误翻范围。

真实案例落点：点一个问题，看应该改哪里

这个交互区是为了避免“看到一个问题就改全局阈值”。每个问题都应该落到具体层。

验证标准：每次改动都要能证明没有跷跷板

内容识别规则是高影响区域，不能只看当前页面截图变好了。要同时跑正向和反向样本。
